1. VISION & THE BEAUTY OF STORY RAIDS
================================================================================

THE PROBLEM WE'RE SOLVING
--------------------------
Reading novels is traditionally a solitary, passive experience. Readers consume
content alone, with no way to influence the story or connect with others who
share their passion. Writers create in isolation, unable to see real-time
community engagement or reward their most dedicated fans.

Even with our read-to-earn model, the engagement loop is:
  Read → Earn → Leave

We want to transform this into:
  Read → Engage → Connect → Compete → Earn → Return

THE BEAUTY OF STORY RAIDS
-------------------------
Story Raids transforms passive reading into active participation by turning
story moments into community events. Here's why this is beautiful:

1. READERS BECOME PARTICIPANTS
   - Instead of just reading about a battle, readers JOIN the battle
   - Their choices actually matter (even if fictional)
   - They develop affinity with characters through actions, not just reading
   - They feel ownership over the story world

2. WRITERS GET REAL-TIME FEEDBACK
   - See which characters readers love most (via faction choices)
   - Understand what plot points excite the community
   - Can adapt future chapters based on raid outcomes
   - Get instant validation when readers engage deeply

3. COMMUNITY FORMS ORGANICALLY
   - Factions create natural "teams" and rivalries
   - Readers discuss strategy, predictions, and lore
   - Discord/Twitter war rooms emerge naturally
   - New readers are pulled in by the excitement

4. RETENTION MULTIPLIES
   - Readers return to check raid progress
   - They want to see if their faction is winning
   - They discuss raids with friends
   - They anticipate the next raid trigger

5. SKILL & LOVE ARE REWARDED
   - Not pay-to-win - cosmetic rewards only
   - Deep readers who understand the story have advantage
   - Engagement matters more than wallet size
   - Badges and titles showcase dedication

THE EMOTIONAL HOOK
------------------
Imagine reading a chapter where the protagonist faces a critical choice:
  "The Crimson Gate stands before you. Behind it, the enemy prepares their
   final ritual. You have 48 hours to decide: breach with force, infiltrate
   stealthily, or negotiate with the gatekeeper?"

Instead of turning the page to find out what happens, YOU get to vote.
You join thousands of other readers in a real-time event. You choose your
faction (Hunters, Rebels, or Scholars). You debate strategy in comments.
You watch the leaderboard shift as more readers join.

When the raid ends, the author writes the NEXT chapter based on what happened.
If Hunters won, the chapter shows a brutal assault. If Rebels won, it shows
a cunning infiltration. YOUR choice shaped the story.

That's the beauty of Story Raids.

3. TECHNICAL ARCHITECTURE OVERVIEW
================================================================================

TECH STACK
----------
- Frontend: Next.js 16 (App Router) + React Bootstrap
- Backend: Supabase (Postgres + Auth + Realtime + Edge Functions)
- Storage: Supabase Storage (images, assets)
- Wallet: Existing Solana integration (for reward distribution)

CORE TABLES (MVP)
-----------------
1. raids - Raid configuration and status
2. raid_factions - Faction definitions per raid
3. raid_participation - User faction membership
4. raid_leaderboard - Computed faction scores

CORE TABLES (V2+)
-----------------
5. user_choices - Individual user actions (missions, predictions)
6. character_affinity - User-character relationship tracking
7. raid_rewards - Reward definitions and claims
8. raid_analytics - Engagement metrics for authors

REALTIME INFRASTRUCTURE
-----------------------
- Supabase Realtime subscriptions on:
  * raids (status updates)
  * raid_participation (faction counts)
  * raid_leaderboard (score updates)
- Optimistic UI updates for responsiveness
- Periodic sync for data consistency

EDGE FUNCTIONS
--------------
- end_raid: Calculate winners, distribute rewards, update analytics
- calculate_scores: Periodic leaderboard recalculation
- anti_bot_check: Behavioral analysis for suspicious patterns

4. MVP (PHASE 1) - FOUNDATION
================================================================================

TIMELINE: 2-3 weeks
GOAL: Prove the core concept works

FEATURE SCOPE
-------------

1. RAID CREATION (Author Dashboard)
   - Simple form to create a raid
   - Fields: title, description, start time, end time, chapter trigger
   - Create 2-3 factions (name, color, description)
   - Set reward amounts (tokens + badge)
   - Status: upcoming → active → ended

2. RAID PARTICIPATION (Reader Experience)
   - Notification on chapter page when raid is available
   - Faction selection modal (animated cards)
   - Join faction (one-time choice per raid)
   - View current raid status from profile

3. LEADERBOARD (Real-time-ish)
   - Display faction scores (member count × points)
   - Update every 30 seconds (not true real-time for MVP)
   - Show top contributors per faction
   - Progress bars for visual appeal

4. RAID COMPLETION
   - Automatic end when time expires
   - Determine winning faction (highest score)
   - Distribute rewards to winning faction members
   - Update user profiles with badges
   - Show results page with statistics

5. BASIC ANTI-BOT
   - Rate limiting (max 1 action per second per user)
   - Chapter verification question (must answer to join)
   - Device fingerprinting (basic)
   - Manual review flag for suspicious patterns

DATABASE SCHEMA (MVP)
---------------------

CREATE TABLE raids (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id UUID REFERENCES novels(id),
  chapter_trigger INTEGER, -- Which chapter triggers this raid
  title TEXT NOT NULL,
  description TEXT,
  starts_at TIMESTAMPTZ NOT NULL,
  ends_at TIMESTAMPTZ NOT NULL,
  status TEXT DEFAULT 'upcoming', -- upcoming, active, ended, archived
  winning_faction_id UUID,
  reward_tokens BIGINT DEFAULT 100,
  reward_badge TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE raid_factions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  raid_id UUID REFERENCES raids(id) ON DELETE CASCADE,
  name TEXT NOT NULL, -- e.g., "Hunters", "Rebels"
  color TEXT NOT NULL, -- Hex color for UI
  description TEXT,
  member_count INTEGER DEFAULT 0,
  score BIGINT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE raid_participation (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,
  raid_id UUID REFERENCES raids(id) ON DELETE CASCADE,
  faction_id UUID REFERENCES raid_factions(id) ON DELETE CASCADE,
  joined_at TIMESTAMPTZ DEFAULT NOW(),
  points_earned INTEGER DEFAULT 0,
  verification_answer TEXT, -- Anti-bot check
  UNIQUE(user_id, raid_id)
);

CREATE INDEX idx_raids_status ON raids(status);
CREATE INDEX idx_raids_novel ON raids(novel_id);
CREATE INDEX idx_participation_user ON raid_participation(user_id);
CREATE INDEX idx_participation_raid ON raid_participation(raid_id);

USER FLOWS (MVP)
----------------

FLOW 1: AUTHOR CREATES RAID
1. Author navigates to /author/dashboard
2. Clicks "Create New Raid"
3. Fills form: title, description, chapter number, start/end times
4. Adds 2-3 factions (name, color, description)
5. Sets reward amounts
6. Clicks "Create Raid"
7. Raid saved with status "upcoming"

FLOW 2: READER DISCOVERS RAID
1. Reader navigates to chapter that triggers raid
2. HUD appears: "Crimson Gate Invasion starts in 2h!"
3. Reader clicks "Join Raid"
4. Faction selection modal appears
5. Reader answers verification question
6. Reader selects faction
7. Reader joins - sees confirmation and current standings

FLOW 3: READER TRACKS RAID
1. Reader navigates to /raids/[raidId]
2. Sees leaderboard with faction scores
3. Sees their faction and contribution
4. Leaderboard updates every 30s
5. Reader can share raid link to recruit others

FLOW 4: RAID ENDS
1. Cron job detects raid end time
2. Edge function calculates winner
3. Rewards distributed to winning faction
4. Badges added to user profiles
5. Raid status changes to "ended"
6. Results page available

2. FactionPickerModal
   - Animated faction cards
   - Faction descriptions

3. RaidDashboard (/raids/[id])
   - Leaderboard with progress bars

4. RaidResults (/raids/[id]/results)
   - Winning faction announcement
   - Final scores
   - Top contributors

5. AuthorRaidCreator (/author/raids/create)
   - Form with all raid fields

5. V2 (PHASE 2) - DEPTH & ENGAGEMENT
================================================================================

TIMELINE: 4-6 weeks after MVP
GOAL: Add strategic depth and more engagement mechanics

NEW FEATURES
------------

1. CHOICE MISSIONS
   - During raids, readers make choices that affect faction score
   - Example: "Send scouts (risk: -10 points, reward: +50 if successful)"
   - Choices have risk/reward mechanics
   - Results revealed after raid ends
   - Adds strategy beyond just joining a faction

2. PREDICTIONS SYSTEM
   - Readers predict raid outcomes before they happen
   - Example: "Which faction will win?" "What will the final score be?"
   - Correct predictions earn bonus points
   - Confidence slider (higher confidence = more points)
   - Encourages readers to analyze and discuss

3. CHARACTER AFFINITY
   - Readers build affinity with characters through actions
   - Affinity unlocks special content (character POV chapters)
   - High affinity readers get exclusive rewards
   - Creates long-term engagement beyond single raids

4. ADVANCED LEADERBOARDS
   - Individual contributor rankings
   - Faction vs faction head-to-head stats
   - Historical raid performance
   - Achievement badges for consistent performance

5. REAL-TIME CHAT INTEGRATION
   - Raid-specific chat rooms
   - Filter comments by #raid hashtag
   - Strategy discussion
   - Live reaction to events

6. NOTIFICATIONS
   - Push notifications when raid starts
   - Alerts when faction is losing
   - Reminders before raid ends
   - Victory/defeat notifications

DATABASE ADDITIONS (V2)
------------------------

CREATE TABLE user_choices (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id),
  raid_id UUID REFERENCES raids(id),
  choice_type TEXT, -- 'mission', 'prediction'
  choice_data JSONB, -- {mission: "scout", prediction: "hunters", confidence: 0.8}
  points_earned INTEGER DEFAULT 0,
  is_correct BOOLEAN,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE character_affinity (
  user_id UUID REFERENCES users(id),
  novel_id UUID REFERENCES novels(id),
  character_id TEXT, -- Character identifier
  affinity INTEGER DEFAULT 0, -- 0-1000
  actions_count INTEGER DEFAULT 0,
  last_action_at TIMESTAMPTZ,
  PRIMARY KEY (user_id, novel_id, character_id)
);

CREATE TABLE raid_notifications (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  raid_id UUID REFERENCES raids(id),
  user_id UUID REFERENCES users(id),
  type TEXT, -- 'start', 'losing', 'ending', 'result'
  sent_at TIMESTAMPTZ DEFAULT NOW(),
  read_at TIMESTAMPTZ
);

DATABASE ADDITIONS (V3)
------------------------

CREATE TABLE puzzle_hunts (

  chapter_id INTEGER,
  clue_text TEXT,
  solution_hash TEXT, -- Hashed solution for verification
  points_reward INTEGER,

  created_at TIMESTAMPTZ DEFAULT NOW()

CREATE TABLE chapter_variants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id UUID REFERENCES novels(id),
  chapter_number INTEGER,
  variant_letter TEXT, -- A, B, C
  raid_outcome TEXT, -- Which raid outcome triggers this
  content_path TEXT, -- Storage path
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE scene_cards (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  raid_id UUID REFERENCES raids(id),
  title TEXT,
  image_path TEXT,
  description TEXT,
  rarity TEXT, -- common, rare, epic, legendary

  created_at TIMESTAMPTZ DEFAULT NOW()

CREATE TABLE user_card_collection (
  user_id UUID REFERENCES users(id),
  card_id UUID REFERENCES scene_cards(id),
  obtained_at TIMESTAMPTZ DEFAULT NOW(),

);

CREATE TABLE global_ranks (
  user_id UUID REFERENCES users(id) PRIMARY KEY,
  rank_title TEXT DEFAULT 'F-rank Reader',
  total_raids_participated INTEGER DEFAULT 0,
  raids_won INTEGER DEFAULT 0,
  total_points_earned BIGINT DEFAULT 0,
  accuracy_pct DECIMAL DEFAULT 0,
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE raid_analytics (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  raid_id UUID REFERENCES raids(id),
  total_participants INTEGER,
  faction_distribution JSONB,
  avg_session_duration_seconds INTEGER,
  retention_rate DECIMAL,
  social_shares INTEGER,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

9. RISK MITIGATION
================================================================================

TECHNICAL RISKS
---------------
RISK: Realtime scaling issues
MITIGATION: Start with polling (30s), upgrade to true realtime after validation
Fallback: Leaderboard updates every 5 minutes if realtime fails

RISK: Database performance under load
MITIGATION: Proper indexing, read replicas, caching
Fallback: Disable non-critical features during peak load

RISK: Edge function failures
MITIGATION: Retry logic, dead letter queue, manual override
Fallback: Admin can manually distribute rewards

PRODUCT RISKS
--------------
RISK: Low user adoption
MITIGATION: Start with popular novels, author incentives, promotional raids
Fallback: Pivot to simpler mechanics or different feature

RISK: Factions become unbalanced
MITIGATION: Auto-balancing algorithms, faction caps, handicap system
Fallback: Merge factions or reset raid

RISK: Writers find it too complex
MITIGATION: Simplified author tools, templates, tutorials
Fallback: Platform team creates raids for writers

SECURITY RISKS
--------------
RISK: Bot farms exploit rewards
MITIGATION: Behavioral analysis, device fingerprinting, CAPTCHA
Fallback: Manual review, ban suspicious accounts

RISK: Coordinate cheating (Discord groups)
MITIGATION: Rate limiting, randomized rewards, delayed results
Fallback: Disqualify coordinated groups

RISK: Smart contract vulnerabilities (if NFTs used)
MITIGATION: Audit contracts, start with off-chain only
Fallback: Keep rewards off-chain until proven secure

OPERATIONAL RISKS
-----------------
RISK: Author creates inappropriate content
MITIGATION: Content review queue, community reporting
Fallback: Takedown process, account suspension

RISK: Toxic behavior in chat/raids
MITIGATION: Automated filtering, moderation tools
Fallback: Disable chat for specific raids/users

RISK: Cost overruns (Supabase, Edge Functions)
MITIGATION: Monitoring, cost alerts, usage limits
Fallback: Downgrade features, increase prices
